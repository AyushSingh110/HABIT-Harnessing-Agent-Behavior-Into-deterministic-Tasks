## 1. Executive Overview

HABIT is a self-optimizing runtime layer for LLM agents. It records agent runs as structured
**trajectories**, **clusters** the recurring ones, **compiles** each recurring recipe into a
deterministic, LLM-free **habit**, **replay-validates** the habit before trusting it, **induces
per-step context (memory) policies** from the recorded access patterns, and at runtime **routes** a
task to a habit while a **divergence detector** watches each step and **falls back** to the live agent
if anything is off — then **recompiles** when the world drifts.

**What is actually built (🟢):** all four layers + an evaluation suite, ~48 source modules, **199
tests** (all offline, mypy-strict, ruff-clean). Real cost/latency has been measured on real models
(Groq `gpt-oss-20b`; local Ollama `qwen3:8b` and `llama3.1:8b`). Figures are generated by
`scripts/make_figures.py`.

**What is NOT built (🟠/🔴):** a persisted habit registry, the XGBoost/value-range divergence detector,
embedding/HDBSCAN fuzzy clustering, a second framework adapter (OpenAI Agents SDK), the FastAPI/React
demo, real context capture from a *generic* LangGraph agent, and OpenTelemetry span emission. These are
proposal items, not code.

## 2. Project Idea in Simple Language

**Simple:** Today's AI agents redo every task from scratch, calling a costly model at every step — even
work they've done correctly a thousand times. HABIT watches them, learns the repeated recipe, and turns
it into cheap code that runs without the model, calling the full agent back only when something new
happens.

**Analogy:** A new employee thinks hard about every task on day one; after a thousand repetitions they
do it on muscle memory and only stop to think when something unusual appears. HABIT gives an agent that
muscle memory.

**Technical:** HABIT is a trace-driven compiler + a runtime safety net + a learned context-management
policy, applied to tool-calling agents, with the compiler coupled to the memory policy (both induced
from the same traces).

## 4. Complete Architecture

Four layers, strict boundaries (mirrors `CLAUDE.md`):

- **L1 Recorder** (`src/habit/recorder/`, `src/habit/adapters/`, `src/habit/storage/`,
  `src/habit/schemas/`) — capture a run as a `Trajectory`, persist it.
- **L2 Compiler** (`src/habit/compiler/`) — cluster → induce skeleton → crystallize habit →
  replay-validate.
- **L3 Context** (`src/habit/context/`) — induce per-step liveness policy → paging simulation →
  safety-validate.
- **L4 Runtime** (`src/habit/runtime/`) — route → run monitored habit → fall back → recompile on drift.
- **Supporting** — `workloads/` (synthetic tasks + pure-code checkers), `baseline/` (the live agent +
  models), `eval/` (corpus, benchmark, injection, long-horizon, research, baselines), `interfaces.py`
  (the `TrajectoryStore` protocol).

See `docs/ARCHITECTURE.md` (diagram) and `docs/HOW_IT_WORKS.md` (mechanisms) — this document
supersedes neither; it audits and expands them.

## 6. Trajectory System

**Simple:** the complete diary of one run. **Analogy:** a CCTV recording of an employee doing one job.
**Technical:** a frozen Pydantic v2 `Trajectory` (`schemas/trajectory.py`).

Concrete example (a refund-ticket run), fields that **actually exist**:
- `trajectory_id: str`, `domain: str`, `task_type: str`, `task_input: dict`, `metadata: dict`,
  `started_at`/`ended_at` (tz-aware), `schema_version`.
- `context_items: list[ContextItem]` — each `item_id`, `kind` (DOCUMENT/TOOL_RESULT/MESSAGE/SYSTEM/OTHER),
  `produced_by_step`, `content_hash`, `size_tokens`.
- `steps: list[Step]` — each `step_index`, `step_type` (LLM_CALL/TOOL_CALL/OTHER), `llm_call`
  (`provider, model, input_tokens, output_tokens`), `tool_call` (`tool_name, call_id, arguments,
  result, error`), `tool_result_schema_fingerprint`, `context_available`, `context_reads`,
  `started_at`/`ended_at`.
- `outcome: Outcome(success, final_output, error, ground_truth_match)`.

**Fields that do NOT exist** (so don't claim them): per-step latency in ms as a number (we have
timestamps; latency is computed in the benchmark, not stored as a field), agent "state" blobs,
embeddings. `run_id` as a separate field does not exist — `trajectory_id` is the run identifier.

Invariants enforced by the schema: LLM step ⇒ `llm_call` set / `tool_call` None (and vice-versa);
fingerprint present iff a tool result exists; `context_reads ⊆ context_available`; every referenced
`item_id` exists in `context_items`; timestamps must be tz-aware.

## 7. Database & Storage

- **Technology:** SQLAlchemy 2.x over **SQLite by default** (`DATABASE_URL=sqlite:///habit.db`),
  PostgreSQL by changing that one env var (no code change). `storage/store.py`, `storage/models.py`.
- **Schema — one table, `trajectories`** (`storage/models.py`): `trajectory_id` (PK, str), `domain`
  (indexed), `task_type`, `success` (indexed, from `outcome.success`), `started_at` (indexed, UTC),
  `payload` (JSON — the full trajectory).
- **How trajectories are stored:** the whole object is serialized (`model_dump(mode="json")`) into the
  JSON `payload`; scalar columns are duplicates used only for fast filtering/ordering. Read back
  losslessly via `Trajectory.model_validate(row.payload)` (`storage/store.py.get`).
- **Retrieval:** `query(domain=…, task_type=…, success=…, limit=…)` (AND filters, ordered by
  `started_at`), `get(id)`, `count(...)`.
- **Habits are NOT stored.** There is no habits table. A `CompiledHabit` is an in-memory object; the
  router holds `{domain: HabitPlan}` in memory. Versioning, staleness flags, and a persisted registry
  are 🟠 planned, "Not verified from the current repository."
- **Embeddings:** none stored (no embedding model used). Vector DB: 🔴.

## 8. Habit Discovery

**How similar runs are grouped (`compiler/clustering.py`):** by an **exact structural signature** —
the ordered tuple `(step_type, tool_name)` over the steps. Not embeddings, not keyword similarity, not
metadata, not a classifier. Runs with an identical signature form one cluster.

Worked example:
```
Traj 1: A → B → C → D
Traj 2: A → B → C → D
Traj 3: A → B → X → D
Traj 4: A → B → C → D
```
`structural_signature` gives Traj 1/2/4 the same signature (one cluster of 3) and Traj 3 a different
one (its own cluster). `cluster_purity(clusters, labels)` measures how cleanly clusters map to a known
label (e.g. domain). On our corpus this recovers one cluster per domain at purity 1.0.

**Limitation (be honest):** exact-signature grouping means a task with a genuinely *different* tool
order lands in a different cluster; there is no fuzzy/embedding clustering yet (🟠). It's the right v1
because our baselines have one clean recipe per domain.

## 9. Habit Compilation (skeleton extraction)

`compiler/skeleton.py` → `induce_skeleton(cluster, trajectories_by_id)` → a `Skeleton` of
`SkeletonStep(index, step_type, tool_name, context_reads, result_fingerprint, stable)`.

For each step position across the cluster it computes what is **stable**: the common `context_reads`
and the common `tool_result_schema_fingerprint`. A step is `stable=True` only if it is a TOOL step
whose reads and result-shape are identical across every run.

Example (invoice-style):
```
Run 1: extract → validate → store → ...
Run 2: extract → validate → store → ...
Run 3: extract → validate → fraud_check → store → ...   (different signature → different cluster)
```
Within one cluster (same signature), the common steps become the skeleton; a step whose result shape
varies (e.g. report's `aggregate`, whose output dict keys depend on the data) is correctly flagged
`stable=False` / `result_fingerprint=None`. That distinction feeds Layer 4 (only shape-stable steps
have a fingerprint to check).

There is **no `difflib`/multiple-sequence-alignment** in the code — alignment is unnecessary because
clustering already groups identical signatures. (Proposal mentioned difflib; not implemented, 🔴.)

## 10. Code Generation — where the habit's "code" comes from

This is the most commonly misunderstood part, so be precise:

**HABIT does NOT generate Python source and does NOT use an LLM to write code.** Instead
(`compiler/crystallizer.py`):
1. **Provenance induction (value-matching):** for each tool argument and each final-output field, it
   finds where the value comes from by matching recorded values across the cluster to: an input field,
   the whole input, a prior tool result's field, a whole prior result, or a constant — first match in
   that priority order wins. Each becomes a typed `Source`.
2. The result is a **`HabitPlan`** = ordered tool steps (each with `arg_sources`) + an
   `output_assembly` map.
3. **Execution** is a **pure interpreter**, `run_habit(plan, task_input, tools)`: it resolves each
   argument from its `Source`, calls the tools in order, and assembles the output. No LLM, no
   `eval`/`exec`.

So the "generated habit" is a **compiled data structure interpreted deterministically**, not emitted
source. (This maps to your prompt's "Method A, graph-to-code," done as a plan+interpreter rather than
text codegen.)

Which parts stay LLM calls: in these three synthetic domains, **none** — every step is a deterministic
tool, so the compiled habit is 100% LLM-free. In a domain with a genuine judgement step, that step
would remain a (small) model call; the mechanism to keep such a step is designed but **not exercised**
(🔵), because our domains don't need it.

Verified: a habit compiled on `seed=0` runs correct on **unseen** `seed=99` tasks (150/150) — evidence
it captured *structure/provenance*, not memorized values.

## 11. Replay Validation

`compiler/validation.py`. `compile_habit(cluster, by_id, tools, validation_fraction=0.3)`:
splits the cluster into train/held-out, crystallizes on train, and runs `validate_habit` on the
held-out trajectories — re-running the habit and requiring its output to **equal the recorded correct
output** on every held-out run whose `ground_truth_match is True`. The returned `CompiledHabit.usable`
is a **read-only property** = `validation.passed`, so a habit can never be marked usable without
passing (the hard rule, enforced structurally). A deliberately broken plan is rejected (tested).

## 12. Runtime Router

`runtime/router.py`. `build_router(compiled)` admits **only** habits whose `.usable` is True, keyed by
domain. `Router.route(domain, task_input)` returns the `HabitPlan` iff (a) a usable habit exists for the
domain, and (b) the task supplies every **input-field** key the plan needs (a cheap applicability
check); otherwise `None` = "run the live agent."

- **Matching mechanism:** exact domain key + input-field presence. **No embeddings, no similarity
  threshold** (🟠 for semantic routing). "Confidence threshold" from the proposal is **not
  implemented** — routing is a deterministic lookup + applicability check.

---

## 13. Divergence Detection

`runtime/divergence.py`. `run_habit_checked(plan, expected, task_input, tools)`:
- wraps the tools to record each result in call order, runs the **same** `run_habit` interpreter,
- then compares each tool result's `schema_fingerprint` to the skeleton's expected fingerprint
  (`expected_tool_fingerprints(skeleton)`); a **mismatch** → divergence. A run that **fails to execute**
  (a result shape broke a later step) is also divergence (one sanctioned `try/except` converts a
  failure into the fallback signal).
- Steps with `result_fingerprint=None` (legitimately variable shape) are skipped — no false alarm.

"Off-script" concretely = a tool's output **shape** changed. Example — expected `{"status": str}`,
actual `{"error": str}` → different fingerprint → caught. **Value-only anomalies** (same shape, wrong
value) are **not** caught by v1 (measured: 0% value catch) — that blind spot is the explicit motivation
for the v2 detector (🟠). Mechanisms implemented: **structure-fingerprint check only.** Embedding
distance, feature-classifier, anomaly detection: 🔴.

---

## 14. Fallback / Re-inflation

`runtime/loop.py`. `run_task(...)`: route → if a plan applies, `run_habit_checked`; if it did NOT
diverge, return the habit output (mode `"habit"`); if it diverged, run the **live baseline agent** and
return its output (mode `"fallback"`); if no plan applied, run the live agent (mode `"live"`).

**Honest detail:** fallback **re-runs the whole task with the live agent** — it does **not** re-inflate
paused-habit state and continue from the failure point. For these **stateless** domains that is correct
(the tools are pure; re-running yields the correct result and the live agent copes with the anomaly).
"State preservation / continue-from-failure-point / duplicate-action avoidance" from the proposal are
**not implemented** (🟠) and are only needed for stateful/side-effecting tools. The fallback run is
recorded (it goes through the recorder), which is what feeds recompilation.

## 15. Context Compiler

`context/policy.py`. `induce_context_policy(cluster, by_id)` does **liveness analysis** over the
recorded `context_reads`/`context_available`:
- per step, union of items read and items available across the cluster;
- `last_read[item]` = the last step index that reads it;
- at step *i*: **live** = available items with `last_read ≥ i` (needed now or later); **evictable** =
  available − live (never read again).

`context/paging.py`. `simulate_paging(policy, sizes)` → per-step and peak window token load for naive
(keep-everything) vs policy (keep-live); `survives(trace, budget)` → whether each stays under a budget.
**`sizes` is a caller-supplied per-item token map** — real tiktoken sizing is **not** wired (🟡).

Example (the long-horizon scenario, `eval/long_horizon.py`): a chain where each step reads only the
previous result + a pinned goal → the policy keeps ~2 items while naive grows to *n*. Measured savings
90/96/98% at n=20/50/100 with a proven-safe policy.

## 16. Memory Architecture

**Simple:** the LLM's context window is a small desk; HABIT decides what stays on the desk each step.
**Analogy:** an OS deciding what's in RAM vs paged to disk. **Technical:** a per-step **keep-live /
evict-dead** policy learned from observed reads (§15), plus a held-out **safety gate**
(`context/validation.py`): a policy is `safe` only if, on held-out runs, no step ever reads an item the
policy would have evicted (zero "starvations"). Retrieval/prefetch: the policy identifies what each step
needs; an actual external-store fetch-back mechanism is **simulated** for measurement, not wired to a
live KV store (🟡). Relevance is **structural (liveness), not semantic** — no embeddings.

## 18. Model Architecture

- **`LargeModel` protocol** (`baseline/model.py`): `provider`, `model`, `complete(prompt)->LLMResponse

- **FakeModel** (🟢, offline default) — deterministic, for tests + structural benchmarks.

- **OllamaModel** (🟢, `baseline/ollama_model.py`) — real local model, lazy `ollama` import.
- **Small model / embedding model / classifier:** 🔴 not implemented. Our habits are fully deterministic
  (no residual small-model step), so a "junior LLM" isn't wired; embeddings and an XGBoost classifier

Analogy: large LLM = senior employee; deterministic habit = a checklist the senior wrote after doing
the job 1000×; HABIT runtime = the manager choosing checklist-vs-senior per task. (There is currently
no "junior employee" small model in the loop.)

## 19. Complete Example (traced through the real code)

Refund ticket, end to end:
1. `TicketWorkload.generate` → a `WorkloadTask`.
2. `run_ticket_baseline` (live agent) runs the authored workflow; `BaselineTrace` records each LLM/tool
   step, `context_reads`, timings, fingerprints; `outcome.ground_truth_match` set by the pure-code
   `TicketWorkload.checker`. → `Trajectory` saved to the store.
3. `generate_corpus` repeats this 1000× → corpus in `habit.db`.
4. `cluster_trajectories` → the ticket cluster; `induce_skeleton` → the ticket skeleton;
   `crystallize` → a `HabitPlan`; `compile_habit` → `CompiledHabit` (usable after held-out replay).
5. `induce_and_validate_policy` → a safe context policy for the ticket recipe.
6. `build_router({"ticket": compiled})`.
7. New ticket → `run_task`: `Router.route` → `run_habit_checked` (0 LLM calls) → if clean, return
   (mode "habit"); if a tool's shape is off, `run_task` runs the live agent (mode "fallback").
8. The fallback's new trajectory is recorded; if `DriftMonitor.is_drifting()`, recompile from fresh
   trajectories.

## 20. First Run → 1000th Run

- **Run #1–#N (training):** the live agent handles everything; every run is recorded. (In our runs the
  corpus is generated up front by `generate_corpus`.)
- **After enough runs:** `compile_habit` produces a validated habit for the recipe.
- **Steady state:** `run_task` serves matching tasks via the habit at **0 LLM calls**; only novel/off
  tasks hit the live agent.
- **Run #1001 (novel):** router finds no habit (or the divergence detector fires) → fallback to the live
  agent → recorded → feeds the next recompile.

There is no automatic "compile after k runs" daemon; compilation is invoked explicitly (offline). That
scheduling is 🟠.

## 21. Cost Model (with REAL measured numbers)

Cost = (# LLM calls) × (tokens/call) × (price) + tool latency. A habit makes **0** LLM calls.

**Measured, real models** (live agent vs compiled habit, `eval/benchmark.py`):
- Groq `gpt-oss-20b`: live 5–6 calls, ~1.6–2.6k tokens, **4.3–17.9 s/task**; habit **0 / 0 / ~0.03 ms**.
- Ollama `qwen3:8b` (CPU): live 5–6 calls, ~1.8–2.0k tokens, **587–722 s/task**; habit 0 / 0 / sub-ms.
- Ollama `llama3.1:8b` (CPU): live 5–6 calls, ~330–390 tokens, **86–208 s/task**; habit 0 / 0 / sub-ms.

All three: habit matches success (1.000) with **100% call + token elimination**. Baseline comparison
(`eval/baselines.py`, FakeModel/structural): vanilla 5 calls, semantic cache 3.5 (only exact repeats),
habit 0.

**Caveat for rigor:** the real runs used tiny eval samples (1–3 tasks); the *structural* result (0 vs
N) is deterministic, but for a paper the live-agent averages need a larger N. Figure numbers
(`figures/results.csv`) are deterministic FakeModel/structural counts, not real tokens.

## 22. Reliability Model

**Theory:** if each step is ~99% reliable, an n-step task succeeds ≈ 0.99^n → drops as n grows (compound
unreliability). HABIT *could* raise reliability by replacing probabilistic steps with deterministic code
plus a safety net.

**Measured:** in our synthetic domains both the live agent and the habit score 1.000 (the mock tools are
correct), so we have **not** demonstrated a reliability *gain* — only cost/latency elimination and
"no regression." Be explicit with the mentor: **reliability improvement is a theoretical expectation
here, not a measured result** (our tools don't fail; a fair reliability study needs flaky steps + pass^k,
which is 🟠).

## 25. HABIT Differentiation / Novelty (honest)

- **Strong novelty:** inducing a **per-step context policy from the same traces** that compile the
  habit (compiler↔memory link), and **validating that policy** (held-out no-starvation gate) the way we
  validate the habit — the dual induced-and-validated gate. No reviewed system does this.
- **Moderate novelty:** the full closed online loop (compile→route→detect→fallback→recompile) for
  **tool-call** agents with **clustered** recipes; a reusable cost/robustness benchmark.
- **Weak/contested:** compile-and-replay itself (PreAct, Compiled AI); divergence+fallback (PreAct);
  the cost result magnitude (impressive but "engineering," and on synthetic data).
- **A reviewer will likely challenge:** synthetic-only workloads; the FakeModel figures; no measured
  reliability gain; exact-signature clustering being "too clean"; habits not persisted.

## 30. Mentor Questions & Answers (with the honest answer)

Format: Q — what they're testing → answer from OUR code → analogy → follow-up.

**Concept**
1. *If you compile behavior to code, why keep an LLM?* — testing determinism understanding → we only
   compile **deterministic tool steps**; genuine judgement steps would stay LLM (our 3 domains happen to
   have none). Analogy: a checklist for routine parts, the expert for novel ones. Follow-up: how do you
   know a step is deterministic?
2. *How do you know a behavior is deterministic?* → we don't infer it in general; the workload's tools
   are deterministic, and the **replay gate** proves the compiled habit reproduces correct outputs on
   held-out runs. A step whose output shape varies is flagged non-stable.
3. *What if two similar tasks need different actions?* → different action sequence → **different
   structural signature → different cluster → different habit**; and at runtime a shape change → divergence
   → fallback.
4. *Isn't this just caching?* → a cache reuses one output for an exact input; HABIT reuses a **general
   recipe** across new parameterizations (measured: reuse 1.0 vs cache 0.3) and **verifies** each step.
5. *Isn't this just RAG?* → RAG retrieves text into a prompt; HABIT removes the model from the hot path
   and manages the *working set* by liveness, not semantic retrieval.

**Architecture / Compiler / Runtime**
6. *Where does the habit's code come from?* → induced `HabitPlan` (provenance by value-matching) run by
   a pure interpreter — **no LLM, no exec** (`crystallizer.py`).
7. *How do you know the generated habit is correct?* → held-out **replay validation**; `usable` only if
   it reproduces correct outputs (`validation.py`).
8. *How do you prevent unsafe code generation?* → we don't generate/execute code strings at all — we
   interpret a typed plan; the only executable is your own registered tools.
9. *How does divergence detection work?* → per-step tool-result **structure fingerprint** vs expected;
   mismatch or run-failure → fallback (`divergence.py`).
10. *What does the detector miss?* → **value-only anomalies** (same shape, wrong value) — measured 0%
    catch; that's why v2 is planned.
11. *What happens on fallback — do you resume mid-run?* → no; we **re-run the task with the live agent**
    (correct for stateless tools); stateful re-inflation is future work.
12. *What happens when a habit goes stale?* → `DriftMonitor` flags a high fallback rate → recompile from
    fresh trajectories (demonstrated in tests).

**Data / Memory / DB**
13. *What's stored and where?* → one `trajectories` table (JSON payload + indexed columns), SQLite by
    default; **habits are in-memory**.
14. *How is context managed?* → learned per-step **liveness** policy (keep-live/evict-dead), safety-gated
    on held-out runs; no embeddings.
15. *Why can't the LLM decide what to remember?* → it can (that's MemGPT) but it **costs a model call
    and is reactive**; ours is deterministic, free, and predictive from observed usage.

**Reliability / Cost / Research / Benchmark**
16. *How do you measure success?* → pure-code ground-truth checkers per domain (`ground_truth_match`).
17. *Prove the cost saving.* → real Groq/Ollama runs: 0 vs 5–6 calls, 0 vs ~2k tokens, sub-ms vs
    seconds–minutes.
18. *Have you shown a reliability gain?* → **not yet** — theory only; our tools don't fail. (Say this.)
19. *What's the actual research contribution?* → the compiler↔memory link + dual induced-and-validated
    gates (§25).
20. *Why not just use PreAct / Temporal / LangGraph / Mem0?* → PreAct = GUI/no memory; Temporal =
    durable execution, not learning; LangGraph = the framework we wrap; Mem0 = conversational facts, not
    procedural working-set. (One line each; details in `HABIT_vs_prior_work.md`.)

(Extend from these patterns for security/scalability: e.g. *security* — no arbitrary code execution,
only registered tools; *scalability* — SQLite→Postgres by env var, but no distributed/streaming path
yet, 🟠.)

## 39. If I had to explain HABIT to my mentor tomorrow

**Problem:** agents recompute known work every time — expensive, and they overflow their context on long
tasks. **Why it matters:** at scale, inference cost and context limits are what block real deployment.
**What we built:** all four layers — a recorder, a trace-driven compiler, a learned context policy, and
a runtime with a divergence-detection safety net — plus an evaluation suite (199 tests). **What happens
to an LLM call:** on a known task it disappears — the habit runs the tool recipe deterministically with
zero model calls. **Where the code comes from:** we don't generate Python or use an LLM to write code;
we induce a typed plan (which value each step needs) and execute it with a pure interpreter. **How we
know it's safe:** a habit is only used after it reproduces correct outputs on held-out runs, and at
runtime we check each tool result's shape and fall back to the full agent if it's off. **When it fails:**
we re-run the task with the live agent and record it. **Context:** we learn, per step, what to keep vs
evict, and we prove the policy never drops something a step needs. **What we learned from prior work:**
AWM (learn workflows from traces), PreAct/Compiled AI (compile + verify), MemGPT (context paging).
**What's genuinely new:** we induce the *context policy* from the same traces as the habit and validate
it — the compiler↔memory link. **What's implemented:** everything above, offline and tested, with real
cost numbers on Groq and Ollama. **What remains:** a measured reliability gain, a larger real-model run,
the value-anomaly detector, a persisted registry, and the live demo. **Next experiments:** flaky-tool
reliability (pass^k), a bigger Ollama cost run, and the v2 divergence ROC.
